# Jira連携 要求

## 位置づけ

`docs/functional-design.md`7〜8章で設計済みのJira連携(紐付け・要約push)を実装する。当初Phase 2として計画していたが、タスクツリー・エディタ連携強化を先に済ませたため、本ラウンドで着手する。

## 事前に決めた設計判断

- **要約の中身**:対象タスクツリー配下のタスクの**タイトルとステータスを、階層構造が分かる形式(インデント付きテキスト)で並べたもの**とする。ログ本文の抜粋やAIによる自然文要約は行わない。ロジックが単純でテストしやすく、外部API(LLM等)への追加依存も発生しないため
- **認証情報の設定方法**:JiraのインスタンスURL・メールアドレスはVSCodeの拡張設定(`contributes.configuration`)で行う。APIトークンのみ、専用コマンドでその場入力しSecretStorageに保存する(設定ファイルに平文で残さないため)
- **投稿前のプレビュー**:生成した要約テキストをエディタに表示し、必要なら手で編集した上で、確認してからJiraへ投稿する。生成してすぐ自動送信はしない

## 変更・追加する機能の説明

- Jira接続設定:拡張設定にJiraインスタンスURL・メールアドレスの項目を追加。APIトークンを入力しSecretStorageへ保存するコマンド(`taskLog.setJiraApiToken`)
- タスクへのJiraチケット紐付け(`taskLog.linkJiraIssue`):入力したチケットキーをAPIで存在確認し、タスクに紐づける。既に祖先が別のチケットに紐づいている場合は、祖先の要約に含めるかどうか(`includeInAncestorSummary`)を選択する
- 要約生成とJiraへの投稿(`taskLog.pushSummaryToJira`):対象タスクから`jiraIssueKey`を持つ最も近い自身または祖先を探し、その配下のタスクツリーを階層テキストとして組み立てる。部分木が別のチケットに紐づき`includeInAncestorSummary`が偽の場合はその部分木を除外する。生成結果をエディタでプレビューし、確認後にJiraへコメント投稿する

## 今回含めない機能

- Jira側でのチケット・サブタスクの新規作成(引き続き対象外。コメント投稿のみ)
- Jira Server/Data Centerへの対応(Jira Cloudのみ)
- 要約のAIによる自然文生成(前述の通り、タイトル+ステータスの階層テキストのみ)

## ユーザーストーリー

- 調査を始めたタスクに、対応するJiraチケットを紐づけておきたい
- 調査が進んだタイミングで、今の状況をJiraチケットにコメントとして残したいが、文章をゼロから書きたくない
- 生成された内容を投稿前に確認し、必要なら書き足してから送りたい
- 調査中に見つかった別件を、別のJiraチケットとして切り出しつつ、元のチケットの報告にも含めるかどうかを選べるようにしたい

## 受け入れ条件

- 拡張設定にJiraインスタンスURL・メールアドレスを入力できること
- `taskLog.setJiraApiToken`でAPIトークンを入力すると、SecretStorageに保存され、設定ファイルには残らないこと
- `taskLog.linkJiraIssue`実行時、存在しないチケットキーを入力するとエラーになり、紐付けが行われないこと
- 存在するチケットキーを入力すると、タスクに`jiraIssueKey`が設定されること。祖先が既に別のチケットに紐づいている場合、含める/含めないを選べること
- `taskLog.pushSummaryToJira`実行時、対象タスクの自身または祖先から`jiraIssueKey`を解決できない場合はエラーになること
- 生成される要約は、対象タスクツリーのタイトルとステータスが階層構造の分かる形式で含まれること。`includeInAncestorSummary`が偽の別チケット部分木は除外されること
- 投稿前に生成内容がエディタに表示され、確認(または編集)してから投稿を実行する操作になっていること。確認せず自動投稿されないこと
- 実際にJiraチケットへコメントが投稿されること(Jira Cloud REST API v3、Basic認証)

## 制約事項

- `docs/architecture.md`で決めた技術選定(Jira Cloud REST API v3、`fetch`、SecretStorage)に従う
- `docs/development-guidelines.md`のDIパターン・エラー処理規約・破壊的操作の扱いに従う。外部システムへの投稿も「元に戻せない操作」に準じ、確認を挟む
- 既存のPhase 1・タスクツリー連携強化の機能に影響を与えない
- 実装後、`docs/functional-design.md`等の該当箇所を実態に合わせて更新する
